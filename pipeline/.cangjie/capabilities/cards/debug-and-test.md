# 调试与测试

## R — 原文

> "调试的过程就是通过上机发现和排除程序中故障的过程。……不要只看到某一次结果是正确的，就认为程序没有问题。例如，求 c=b/a，当 a=4,b=2 时，求出 c 的值为0.5，是正确的，但是当 a=0,b=2 时，就无法求出 c 的值。说明程序对某些数据能得到正确结果，对另外一些数据却得不到正确结果，程序还有漏洞。"
> ——第1章 §1.6 程序设计的任务（第5阶段）

> "所谓测试，就是设计多组测试数据，检查程序对不同数据的运行情况，从中尽量发现程序中存在的漏洞，并修改程序，使之能适用于各种情况。作为商品提供使用的程序，是必须经过严格测试的。"
> ——第1章 §1.6

## I — 自述

"程序能跑起来"和"程序是对的"是两个完全不同的判断。这本书把它们拆成两个目标不同的活动：

**调试（debug）** 针对的是**已知的失败**——程序报错了、结果不对了，你去定位并排除这个故障。目标是"修好这一个问题"。

**测试（test）** 针对的是**未知的漏洞**——程序看起来正常，你主动设计多组数据去撞它，目的是"找出还没暴露的问题"。目标是"发现问题"，不是"证明没问题"。

这个区分为什么重要？因为人的默认心态是"跑通了就是对的"。原书用一个极简例子打掉这个幻觉：`c=b/a`，取 a=4、b=2 得到 0.5 完全正确；但取 a=0 就没法算了。同一份代码，一组数据对、另一组数据错——所以**一组数据通过不能证明程序正确**。

因此写完之后必须做的是：主动构造多组数据，特别是**边界值**——0、1、负数、数组的第一个和最后一个元素、循环一次都不执行的情形、刚好达到上限的情形。这些地方是漏洞的高发区。

调试阶段还有一个定位工具，来自第1章的「四步流水线」：**编译期报错 = 语法问题**（改语法，重新编译）；**编译通过但运行结果不对 = 逻辑问题**（查公式、查赋值方向、查运算顺序、查边界）。先分清错误属于哪一类，再动手，比盲目改代码快得多。

## A1 — 书中案例

- **`c=b/a` 的例子（原书给出，§1.6）**：a=4,b=2 → c=0.5 正确；a=0,b=2 → 无法求值。原书用这一个例子同时论证了「调试不等于测试」和「必须用多组数据验证」两个结论。
- **例1.3 把 `b=a;` 写成 `a=b;`（原书 §1.6 举例）**：这类错误"不存在语法错误，能通过编译，但运行结果显然与预期不符"——典型的需要靠「运行结果分析」而非「编译报错」来发现的逻辑错误。
- **§1.5 编译出错的循环（原书描述）**：编译报错 → 检查源程序 → 修改 → 重新编译，反复直到无语法错误。这是调试的「编译期」部分，是机械可重复的。

## A2 — 何时触发

用户会在这些情境下：
- 程序跑通了一组数据，但不确定是否真的正确；
- 程序莫名其妙给出错误结果，不知道从哪查起；
- 交作业/上线前想知道还要测什么；
- 遇到「有时对有时错」的间歇性 bug；
- 想建立一套自查清单，避免反复犯同类错误。

语言信号：「程序跑通了是不是就没问题了」「结果不对怎么查」「怎么测试一个C程序」「要不要测边界值」「有时候对有时候错」「assert 怎么用」「怎么调试」「debug 和 test 有什么区别」。

**与相邻能力区分**：本能力管「验证与排错的方法」；如果已经定位到是「循环写错了」→ 用 `control-flow`；是「数组越界」→ 用 `array-and-string`；是「指针乱指」→ 用 `pointer-model`；是「文件数据丢了」→ 用本包内的《文件读写》能力卡。

## E — 执行步骤

**输入契约**：需要①程序的功能与预期行为；②当前观察到的现象（报错原文／错误输出／无输出／崩溃）；③已测过的数据与结果。现象描述不清时应先索要具体输入-输出对。

**输出契约**：交付「错误分类（语法／逻辑／运行时）→ 定位依据 → 修复建议」；测试场景交付「测试数据表（输入／预期／实际／是否通过）」，至少含一组正常值、一组边界值、一组非法或极端值。

步骤：

1. **分类**：报错在编译期 → 语法类，按住错误行号改；能编译但结果错 → 逻辑类；运行时崩溃 → 运行时类（越界、空指针、除零）。完成标准：能说出属于哪一类及依据。
2. **构造最小复现**：把出错的代码缩到最短仍能重现问题。完成标准：删掉无关代码后问题依旧。
3. **定位（逻辑类专用）**：逐项核对——公式与运算顺序、赋值方向、循环边界（`<` 还是 `<=`）、变量初值、`scanf` 是否漏 `&`、格式符与类型是否匹配。完成标准：能指出具体是哪一行哪一处导致偏差。
4. **设计测试数据**（这一步与 3 并行，不要等出错才做）：至少四类——①典型正常值；②边界值（0、1、最大下标、空输入）；③使循环一次都不执行的值；④会触发特殊分支的值。完成标准：每组都有明确的预期输出，可机械比对。
5. **执行并比对**：逐组运行，记录实际输出与预期的差异。完成标准：形成完整测试表，无"跑过就算"的省略项。
6. **修复后回归**（判停点）：改完必须重跑**全部**测试数据，而不是只跑刚才失败的那一组——修一处引入另一处错误是常见情况。
7. **归纳**：把本次踩的坑记入个人错误清单，避免重复。完成标准：能说出"下次遇到同类场景要检查什么"。

## B — 边界

- **不适用**：程序还在设计阶段、功能都没定型时，先不要陷入测试细节；此时该做的是 `algorithm-design`。
- **作者盲点**（阶段 0 批判）：本书的测试方法停留在「手工设计数据、逐组运行比对」的黑盒层面，**不涉及**单元测试框架（如 Unity、CUnit）、断言库、覆盖率工具、模糊测试、静态分析、sanitizer（ASan/UBSan）。原书也明确把「常见错误分析」整章移到了配套辅导书。用户若需要工程化测试，应说明本书只提供方法论起点。
- **易混淆**：①「调试」是修已知故障，「测试」是找未知漏洞，两者目标相反；②「跑通了」≠「正确」，一组数据通过无意义；③编译器的 warning 不等于 error，但「警告」往往指示真实的隐患（如 double 用 `%f` 输入）。
- **失败模式**：只测「happy path」（正常输入），从不测 0、空、负数、上限——这是绝大多数教学程序藏 bug 的地方。
