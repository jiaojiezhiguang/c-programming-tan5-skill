# 算法先行：从任务到算法的设计流程

## R — 原文

> "程序设计是指从确定任务到得到结果、写出文档的全过程。……（1）问题分析。（2）设计算法。（3）编写程序。（4）对源程序进行编辑、编译和连接，得到可执行程序。（5）运行程序，分析结果。（6）编写程序文档。"
> ——第1章 §1.6 程序设计的任务

> "具体说，采取以下方法来保证得到结构化的程序：（1）自顶向下；（2）逐步细化；（3）模块化设计；（4）结构化编码。"
> ——第2章 §2.6 结构化程序设计方法

> "引导读者在处理任务时先考虑算法再编程，而不是坐下来就写程序，养成良好的编程习惯。"
> ——前言「关于本书内容的选择原则与具体安排」

## I — 自述

写程序不是从敲代码开始的。这本书把「做一道编程题」拆成六个阶段，其中前两个阶段完全不碰代码，第四个阶段之后才是机器的事：

1. **问题分析**：忽略次要因素，把问题抽象成模型（常用数学式子表达内在关系）；
2. **设计算法**：选出解题方法，把每一步写清楚，用流程图或伪代码表示出来；
3. **编写程序**：把算法翻译成语言代码（这一步才是"写代码"）；
4. **编辑、编译、连接**：得到可执行程序；
5. **运行并分析结果**：调试（修已知故障）＋测试（主动找漏洞）；
6. **写文档**：名称、功能、运行环境、输入、注意事项。

关键在第 2 阶段的方法。面对一个一下子写不清的复杂任务，不做「提笔就写、想到哪写到哪」，而是**自顶向下、逐步细化**：先做顶层设计（这问题分几大块），再逐层往下分（每一块分几节、每一节分几段），直到每一小块都能直接变成几条语句为止。每向下一层展开**之前**先检查本层是否正确——只有上层对了才往下细化，于是整个算法的正确性由每层的局部正确性累加保证，而不必一次性想清楚全部细节。

细化到一定粒度后，把每个子任务做成独立模块（C 里就是函数）：一个模块只干一件事，模块之间耦合越少越好，单个模块不超过约 50 行。这就是「分而治之」——把大任务切小，每个小任务都简单到能独立想清楚、独立验证。

最后才是**结构化编码**：用只含顺序、选择、循环三种结构的语言，把已经细化好的算法写出来。

算法用什么写下来？设计阶段用**伪代码**最快（书写方便、改动容易，加一行删一行都不费事）；定稿核对结构时用 **N-S 图**（盒图，没有流程线、天然结构化，上下顺序就是执行顺序）；要给别人看或要暴露逻辑错误时用**传统流程图**（直观，但不限流向，容易画成"一碗面条"，且改动麻烦）。三者是不同阶段的工具，不是替代关系。

细化算法时有两个最常用的具体手法：

**其一，把「逐条罗列」改写成「循环」。** 当发现一组操作「每次内容和方法都相似、只是对象不同」时，就该抽象成循环：①找出每次操作中不变的规律；②用一个变量（下标）代表变化的对象；③把重复部分写成循环体，让这个变量遍历全部对象。判据很简单——如果你写完发现步骤数随数据量成正比地膨胀，就该找规律改成循环。

**其二，用三种基本结构拼装。** 顺序（A 完接 B）、选择（按条件走两支之一、汇合于单一出口）、循环（当型：先判断后执行；直到型：先执行后判断）。一个算法是「结构化」的，当且仅当它只有单入口、单出口、且结构内每一部分都存在一条从入口到出口的通路。如果画出来发现某个结构有两个出口（典型是循环里提前跳出），就用**标志变量**把它收敛：设一个开关变量（初值 0），把原本要「立即跳出」的情形改成「置开关为 1」，再把开关并入循环条件，循环自然退出，最后用选择结构按开关值决定输出。这样多出口就变成了「单出口循环 ＋ 一个后续选择」。

## A1 — 书中案例

例 5.1 求 1+2+…+100（原书给出了完整的流程图与运行结果）演示了「先算法后编码」：

- 问题：求 1 到 100 之和；
- **分析与设计**（不写代码的部分）：这是累加问题，要重复 100 次加法 → 用循环；每次加的数有规律（后一个比前一个大 1），所以不必每次 scanf 输入，只需让 i 每次加 1 得到下一个加数。据此画出 N-S 图；
- 编码：按图写成 `i=1;sum=0; while(i<=100){sum=sum+i;i++;}`；
- 结果：输出 `sum=5050`。

对照可见：如果没有第 2 阶段，容易写成「把 100 条加法语句罗列出来」；有了算法设计，才得到 5 行可扩展的循环。

另两个书中案例（均为原书例题，未逐一给出运行结果者标注）：

- **例2.1 求 5!（循环归纳）**：最初写法是「1×2 得 2，再 ×3 得 6，再 ×4…」，求 1×2×…×1000 要写 999 步——原书明确指出"显然是不可取的"。抽象出规律后改为：设 t 存累积结果、i 存当前乘数，循环 `t=t*i; i=i+1;` 直到 i>5。同一个算法改一个初值和条件就能求 1×3×5×7×9×11。
- **例2.15 素数判断的结构化改造（标志变量）**：原流程图（图2.12）中间的循环有两个出口（一个来自"r=0?"判断框，一个来自循环判断框），不能分解为三种基本结构，因此无法直接画 N-S 图。改造办法：引入 `w`（初值 0）当开关，`r=0` 时不马上输出"不是素数"，而是置 `1→w`；把循环条件改为「i≤√n 且 w=0」；循环结束后再用选择结构按 w 的值决定输出。原书对 w 的说明是"w 的作用如同一个开关一样，有两种工作状况：w=0 和 w=1……当 w=1 时表示被检查的数 n 为非素数"。

## A2 — 何时触发

用户会在这些情境下：
- 拿到一道编程题／一个实际需求，不知道怎么下手、从哪开始；
- 复杂功能写成一坨，主函数几百行，改一处牵动全身；
- 想知道「流程图／伪代码／N-S 图到底该用哪个」；
- 想把一个大程序拆成若干函数，但不知道怎么切；
- 直接开始敲代码，写到一半发现思路不对要推翻重来。

语言信号：「这个程序该怎么设计」「拿到题目不知道从哪下手」「怎么把大问题拆小」「流程图和伪代码用哪个」「主函数太长了怎么拆」「top-down design」「先写算法还是先写代码」「how to decompose a programming problem」。

**与相邻能力区分**：本能力管「任务 → 算法 → 模块划分」这条上游链路，负责回答「该切成几块、按什么维度切、每块职责是什么」。若问题已从「切几块」下沉到「这个函数里面怎么写」（参数、返回值、递归实现、值传递）→ 用 `function-and-recursion`；若下沉到「循环/分支语句怎么写、为什么死循环」→ 用 `control-flow`。

## E — 执行步骤

**输入契约**：需要①任务描述（要解决什么问题、输入什么、输出什么）；②规模与约束（数据量级、是否有边界条件）。若任务描述含糊到无法判断输入输出，先追问，不要替用户假设需求。

**输出契约**：交付三段——①问题分析（抽象后的模型，一两句）＋②算法描述（伪代码或 N-S 图，含分支与循环的边界）＋③模块划分表（模块名 / 职责 / 输入 / 输出）。编码是第四步，不在本能力强制交付，但应给出与算法一一对应的代码骨架。

步骤：

1. **问题分析**：写出「输入是什么、输出是什么、要满足什么关系」。完成标准：能用一句话说出问题的数学模型或处理规则。
2. **顶层设计**：把任务分成 3–7 个大块，写出每块的名字。完成标准：每一块都能独立说清"它负责什么"。
3. **逐层细化**：对每块继续往下分，直到每块可直接写成几条语句。完成标准：最底层每块不超过一个基本结构（顺序/选择/循环）能表达的范围。
4. **逐层校验**（判停点）：每细化一层前，先检查上一层是否正确；若发现上层有逻辑漏洞，**退回上一层改**，不要带着错误往下细化。
5. **选表示法记录**：设计期用伪代码快速迭代；算法定稿后用 N-S 图画一遍核对结构。完成标准：N-S 图中不存在无法分解为三种基本结构的片段（若存在，按本卡 B 段「改造法」用标志变量收敛出口后重画）。
6. **模块化划分**：按上一步的子任务列模块表，检查每个模块是否「一件事、≤50 行、低耦合」。完成标准：模块表每一行都能独立测试。
7. **结构化编码**：按 N-S 图逐块翻译为代码。完成标准：代码结构与 N-S 图一一对应，无临时跳转。

## B — 边界

- **不适用**：程序只有三五行的简单脚本、或用户只问某个语法点——不需要兴师动众走六阶段。
- **不适用于纯探索**：如果需求本身还没定型（边写边发现要什么），先做原型验证需求，再回来做正式设计；强行自上而下会设计出错误的结构。
- **作者盲点**（阶段 0 批判）：本书的设计方法论面向「单人小规模教学程序」，不含需求变更管理、接口契约设计、单元测试驱动开发。用户若在真实工程语境，应说明本书方法只是起点。
- **易混淆**：「自顶向下、逐步细化」是**设计**方法；「自底向上、逐步积累」是另一种做法（本书明确不推荐用于设计，但施工/实现阶段本来就是自下而上拼装的）。不要把两者混为一谈。
- **失败模式**：把「细化」做成「提前优化」——在不清楚整体结构时纠结某一行的写法。
