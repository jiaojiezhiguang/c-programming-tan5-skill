# 函数、参数传递与递归

## R — 原文

> "注意：函数就是功能。每一个函数用来实现一个特定的功能。函数的名字应反映其代表的功能。"
> ——第7章 §7.1 为什么要用函数

> "注意：实参向形参的数据传递是'值传递'，单向传递，只能由实参传给形参，而不能由形参传给实参。实参和形参在内存中占有不同的存储单元，实参无法得到形参的值。"
> ——第7章 §7.3.3 函数调用的过程

> "一个递归的问题可以分为'回溯'和'递推'两个阶段。……显而易见，如果要求递归过程不是无限制进行下去，必须具有一个结束递归过程的条件。例如，age(1)=10，就是使递归结束的条件。"
> ——第7章 §7.6 例7.6

## I — 自述

理解函数的最省力方式不是背定义，而是把「函数」当成「一段有名字的功能」。`function` 在英文里既是"函数"也是"功能"，这个双关正是它的本质：函数名就是给某个功能起的名字，函数体就是这个功能的实现。所以好的函数名应当让人一眼知道它做什么（`max`、`swap`、`print_star`），而一个函数只应该干一件事。

用函数解决的是两个问题：**程序太长读不懂**（把主函数拆成若干功能块），和**同样的代码要写很多遍**（写一次、到处调用）。这就是模块化——像组装电脑一样，事先做好各个部件，用的时候取来装上，而不是每次临时生产一个。

定义函数要交代四件事：函数名（叫什么）、函数类型（返回值的类型）、参数的个数与类型（要接收什么数据）、函数做什么（函数体）。如果函数定义在调用它的地方**之后**，调用前必须先**声明**（把函数名、类型、参数规格告诉编译器），否则编译器看到 `max(a,b)` 时不知道 `max` 是什么。这是「定义」与「声明」的区别：定义有函数体、分配了实现；声明只是原型，让编译器能检查调用是否合法。库函数则由头文件提供声明，所以用 `sqrt` 要 `#include <math.h>`。

**参数传递是 C 语言最容易被误解的一点。** 调用函数时，系统把实参的**值**复制给形参，二者占的是不同的存储单元。因此：

- 函数内部怎么改形参，都改不到实参——这叫单向值传递；
- 想通过函数修改调用者的变量，必须传**地址**（指针），在函数里通过 `*p` 改目标单元；
- 但数组是例外中的例外：数组名作实参时，传过去的是**首元素地址**，不是整个数组的副本，所以函数内改数组元素会影响原数组。这看起来像"传引用"，实质仍是值传递——只不过传的"值"是地址。

**递归**是把「大问题」化成「同型的更小问题」的写法，必须有两部分：一个**递归关系**（n 的问题 = n-1 的同类问题 + 一步操作）和一个**终止条件**（基例，到某个值直接给答案，不再递归）。执行过程分两阶段：先是「回溯」——一路把问题展开到基例；然后「递推」——从基例的结果一层层回代，算出最终答案。缺终止条件就是无限递归，直到栈溢出崩溃。

递归不是万能的。凡是递归能写的，用循环＋数组也能写（求 n! 用递推就是从 1 乘到 n）。递归的优势在于「有些问题用循环表达极其别扭」——比如 Hanoi 塔，把 64 个盘子的移动序列直接写出来几乎不可能，但"假设 63 个已经能搬"之后，三步就描述完了。判断该不该用递归，看问题是否「天然同构地降阶」，而不是看它"看起来高级"。

## A1 — 书中案例

- **例8.3 swap 用指针交换（原书给出结果）**：`void swap(int *p1,int *p2){int temp; temp=*p1; *p1=*p2; *p2=temp;}`，调用 `swap(&a,&b)`。若把形参写成 `int p1,int p2` 只交换形参副本，`a`、`b` 不变。原书点明："在函数调用时，将实参变量的值传送给形参变量，采取的依然是'值传递'方式"——形参是指针时，传递的是地址这个值。
- **例7.6 五个学生的年龄（原书给出完整调用过程图）**：`age(n)=age(n-1)+2`，基例 `age(1)=10`。原书追踪了 5 次调用：age(5)→age(4)→…→age(1) 得 10（回溯），再 12→14→16→18 回代（递推）。
- **例7.8 Hanoi 塔（原书给出思路分解）**：不直接求 64 步，而假设"有人能搬 63 个"，于是只需 ①63 个 A→B ②最大盘 A→C ③63 个 B→C。原书原话："假如有另外一个和尚能有办法将上面63个盘子从一个座移到另一座。那么，问题就解决了。"
- **例7.7 递归求 n!（原书给出溢出边界）**：`int` 型在 VC++/GCC 下最大 2147483647，n=12 正常，输入 13 就得不到预期结果——原书提示应改用 `float`/`double`。

## A2 — 何时触发

用户会在这些情境下：
- 主函数越写越长，想把功能拆成若干函数，但不知道怎么切；
- 写了函数来"修改"调用者的变量，结果调用完原变量没变；
- 分不清「函数定义」和「函数声明」，或者把函数写在 main 后面就编译不过；
- 想写递归但写成了死循环／栈溢出，或不知道该在哪里停；
- 纠结「这题该用递归还是循环」；
- 数组传给函数后原数组被改掉了，想不通为什么"值传递"还会改。

语言信号：「函数怎么传参才能改变实参」「为什么我在函数里改了变量外面没变」「函数声明和定义的区别」「undefined reference to」「递归怎么写／递归终止条件」「递归和循环该用哪个」「数组作函数参数」「void 函数要不要 return」「形参实参」「pass by value / pass by pointer」。

**与相邻能力区分**：本能力管「函数组织 + 参数语义 + 递归」。如果问题是「指针本身怎么理解（地址、解引用、基类型）」→ 用 `pointer-model`；是「数组下标/长度」→ 用 `array-and-string`；是「程序该怎么分层设计」→ 用 `algorithm-design`。

## E — 执行步骤

**输入契约**：需要①函数要完成的功能（一句话）与输入输出（参数是什么、返回什么）；②调用场景（在 main 里调、在别的函数里调、跨文件调）；③若是排错，需要函数定义、调用处代码和现象（原变量没变／编译报错／栈溢出）。功能说不清时应先让用户用一句话描述，不要直接写代码。

**输出契约**：交付「函数原型（含类型、参数）→ 函数定义 → 调用示例 → 参数传递说明（值／地址／数组）」。递归场景额外给出「递归关系式 + 基例 + 调用深度估算」。

步骤：

1. **明确功能与契约**：写出「函数名 / 返回类型 / 参数表 / 一句话功能」。完成标准：函数名见名知义；无返回值则类型为 `void`。
2. **判定是否需要返回值带回结果**（判停点）：若只需执行一组操作 → `void`；若需带回一个值 → 用 `return` 且返回值类型与函数类型一致；若需带回**多个**结果或修改调用者变量 → 进入 3 用指针参数。
3. **确定参数传递方式**：
   - 只读输入、不需要改调用者 → 普通值参；
   - 需要改调用者变量 → 指针参数，实参传 `&x`；
   - 传入数组 → 形参写成 `int a[]` 或 `int *a`（等价），并**额外传长度**（C 不知道数组有多大）。
   完成标准：每个参数都能说清「传进来的是值还是地址、函数内会不会改到外面」。
4. **处理定义与调用的顺序**：函数定义在调用点之后 → 在调用前写原型声明。完成标准：编译无「隐式声明」类警告。
5. **递归专项**（若采用递归）：先写递归关系式，再写基例，再估算递归深度是否会导致栈溢出（Hanoi 64 盘是 2^64 量级，仅作演示不可真跑）。完成标准：能指出「哪一行让 n 向基例收敛」。
6. **选择递归还是循环**（判停点）：若问题能用一次遍历（带累加/累乘）表达 → 优先循环（省栈、易懂）；若问题天然「同构降阶」且循环表达极别扭（树、分治、Hanoi）→ 用递归。
7. **验证**：至少测一组正常值、一组基例值、一组极端值（如 n=0、空数组）。完成标准：三组结果均符合预期，且形参/实参的修改行为符合第 3 步的设计。

## B — 边界

- **不适用**：函数体只有一两行且只调用一次——抽成函数反而增加阅读跳转成本。原书建议"程序中的子模块一般不超过 50 行"，是上限而非要求把所有东西都拆碎。
- **作者盲点**（阶段 0 批判）：本书不涉及函数指针的高级用法（仅第8章 §8.5 简介）、可变参数、内联、递归改迭代的显式栈做法。用户若在性能敏感场景，应提示递归可能带来栈与时间开销。
- **易混淆**：①「值传递」与「数组名传地址」不矛盾——传的仍是值，只是这个值是地址；②`return 0;` 只是 main 的返回值，不是所有函数都该写（原书专门提醒"也不要不加分析地在所有函数的最后都写上 return 0;"）；③函数不能嵌套定义，但可以嵌套调用。
- **失败模式**：以为「在函数里改了形参，外面就变了」——这是 C 语言初学者最高频的误解，也是本能力最需要主动预警的点。
- **注意 void**：`void` 函数不需要 `return` 值；但可以写 `return;` 提前返回，这不是错误。
