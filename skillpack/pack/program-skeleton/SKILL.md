## I — 自述

C 程序的骨架是固定的：一行预处理指令（要用标准输入输出就 `#include <stdio.h>`）＋一个 `int main()` 主函数＋`return 0;`。这是任何 C 程序的起点，其余全部内容都是往这个骨架里加东西。

编译器对程序的加工是四步流水线，每一步的产物不同、失败表现也不同，这个对应关系是排错的导航图：

1. **编辑** → 得到 `.c` 源文件；
2. **编译**（先预处理展开 `#include`/`#define`，再检查语法、翻译）→ 得到 `.obj` 目标文件。**语法错误在这一步报**；
3. **连接**（把各目标模块与函数库装配起来）→ 得到 `.exe` 可执行程序。即使只有一个源文件也必须连接库；
4. **运行** → 得到运行结果。**能跑但结果不对，是逻辑错误，在这一步暴露**。

所以看到一个错误时，先问它在哪一步出现的：编译报错就去改语法（缺分号、拼错函数名、变量没定义）；能编译但结果错就去查逻辑（公式写错、赋值方向反了、边界没处理）。

C 程序的书写规则里最容易踩的还是那几条：每个语句以分号结束；`main` 有且只有一个；要用库函数就得包含对应头文件；大小写敏感；注释用 `//`（到行尾）或 `/* */`（可跨行），且字符串里的 `//`、`/*` 不算注释。

## A1 — 书中案例

例1.1（原书提供了运行结果）：

- 问题：在屏幕上输出一行 `This is a C program.`
- 做法：`#include <stdio.h>` 引入 `printf` 的信息 → `int main()` → `printf("This is a C program.\n");` → `return 0;`
- 结果：屏幕输出该行文字，随后 `main` 返回 0。原书说明 `\n` 是换行符，光标移到下一行开头；`return 0;` 把整数 0 作为函数值返回给操作系统，表示主函数正常结束。

## A2 — 何时触发

用户会在这些情境下遇到它：
- 第一次写 C 程序，不知道一个完整程序长什么样、`#include` 和 `main` 各是干什么的；
- 程序编译不过，报错看不懂，想知道错误属于哪一类、该改哪里；
- 程序能编译运行，但结果不对，想知道该往哪个方向查；
- 想知道从 `.c` 到能运行中间到底发生了什么。

语言信号：「写个最简单的C程序」「C程序的基本结构」「`#include <stdio.h>` 是干什么的」「编译报错 error: expected ';'」「为什么程序能运行但结果是错的」「.c .obj .exe 有什么区别」「undefined reference to」「程序有时能跑有时崩溃」「segmentation fault 该从哪查」。

**与相邻能力区分**：本能力只管「骨架 + 工具链 + 错误**分诊**」。注意"分诊"是本能力的职责：遇到「有时能跑有时崩溃」这类现象，先判断是越界（转 `array-and-string`）、野指针（转 `pointer-model`）还是逻辑错，再交出；不要跳过判断直接扑向某一个主题。若用户的诉求已经是具体的「这个算法该怎么设计」→ 用 `algorithm-design`；是「指针为什么这么写」→ 用 `pointer-model`。

## E — 执行步骤

**输入契约**：需要知道①用户是要「新建一个能跑的程序」还是「诊断一个出错程序」；②若是诊断，需要错误信息原文或现象描述（报错文字／运行结果与预期的差异）；③编译环境（Visual C++／GCC／Dev-C++ 等，影响报错措辞与后缀）。缺少错误信息时应先索要，不要凭现象猜测错误类型。

**输出契约**：新建场景交付一份可直接编译的完整源码（含 `#include`、`main`、`return 0;`、必要注释）＋编译运行命令；诊断场景交付「错误归类 → 原因 → 具体改法（改前/改后代码）」三段。

步骤：

1. **判断场景**：是「新建骨架」还是「诊断错误」。完成标准：明确说出接下来走 2 还是走 3。
2. **新建骨架**：按 `#include`（按需）→ `int main()` → 声明部分 → 执行语句 → `return 0;` 的顺序给出完整程序。
   完成标准：程序含且仅含一个 `main`，每条语句以分号结束，用到的库函数都有对应头文件。
3. **定位错误阶段**（判停点）：若报错出现在编译期 → 进入 4（语法类）；若编译通过但运行结果不符 → 进入 5（逻辑类）；若连接期报 `undefined reference` → 进入 6。
4. **修语法错**：按报错行号定位，常见为缺分号、括号不配对、变量未定义、函数名拼错、头文件缺失。完成标准：改后重新编译无 error。
5. **查逻辑错**：核对公式与运算顺序、赋值方向（是否把 `a=b` 写成 `b=a`）、循环边界、变量初值、`scanf` 是否漏 `&`、格式符与类型是否匹配。完成标准：用至少两组数据（含一组边界值）验证结果正确。
6. **修连接错**：确认函数已定义或被正确声明、源文件都已加入工程、需要的库已链接。完成标准：连接成功生成可执行文件。

## B — 边界

- **不适用**：用户已有能正常编译运行的程序、问的是「如何把它设计得更好」——那是算法与结构问题，不是骨架问题。
- **不要越界承诺**：本书基于 C89/C99，示例环境是 Visual C++ 6.0 / VS2010。现代编译器（GCC 13+、Clang）对 `void main`、隐式函数声明等更严格，直接照抄老示例可能报错——遇到时按现代标准修正，并明确告知差异。
- **作者盲点**（阶段 0 批判）：本书不涉及构建系统（Makefile/CMake）、版本控制、sanitizer 等现代工程实践；用户若问这些，应说明超出本书范围。
- **易混淆**：「编译」与「连接」不是一回事（本书反复强调即使单文件也要连接库）；「目标程序」不等于「可执行程序」。
- **失败模式**：只跑通一组数据就宣布程序正确——本书明确说这不叫测试（见 《调试与测试》能力卡）。
